> 数据库题在 SAA 几乎每张试卷都占 6–8 题。**没有"最好的数据库"**,只有"对这个负载最好的数据库"。

## 二、关系型数据库(RDS 家族)

### 2.1 RDS 引擎选择

| 引擎 | 何时选 |
|------|--------|
| **Aurora**(MySQL/PostgreSQL 兼容) | **新项目首选**;比原版 MySQL 快 5×、PostgreSQL 快 3×;存储自动扩展 64 TB;6 副本跨 3 AZ |
| RDS for MySQL / PostgreSQL | 你已经有 MySQL/PG 应用,不想改 |
| RDS for MariaDB | MariaDB 现有生态 |
| RDS for Oracle / SQL Server | 你 license 已经买了,迁移成本高 |
| **Amazon RDS Custom**(Oracle / SQL Server) | 需要 OS 级访问、装 agent、定制 |

### 2.2 高可用 vs 性能 — 两个不同特性

```
            目的不同,别混!
   ┌────────────────────────┐  ┌────────────────────────┐
   │ Multi-AZ (高可用)       │  │ Read Replica (读扩展)   │
   ├────────────────────────┤  ├────────────────────────┤
   │ 同步复制                │  │ 异步复制(可能滞后)     │
   │ 备用副本不可读          │  │ 副本可读(只读)         │
   │ 主挂掉自动 failover     │  │ 不自动 failover         │
   │ 同 Region 跨 AZ         │  │ 同/跨 Region 都可       │
   │ 解决:可用性             │  │ 解决:读性能             │
   └────────────────────────┘  └────────────────────────┘
```

### 题目套路

| 题目说 | 答案 |
|--------|------|
| "数据库可用性 99.95% + 自动 failover" | **Multi-AZ** |
| "读 QPS 太高、CPU 100%" | **Read Replica**(最多 15 个 Aurora,5 个 RDS) |
| "想要跨 Region 灾备" | **Cross-Region Read Replica** 或 **Aurora Global Database** |
| "Aurora 跨 Region < 1 秒灾备 RPO" | **Aurora Global Database**(RPO ~1 秒,RTO < 1 分钟) |
| "无服务器、按 ACU 计费、间歇性负载" | **Aurora Serverless v2** |
| "数据库连接太多、Lambda 突发连接" | **RDS Proxy**(连接复用) |
| "数据库无法支持 100K+ TPS 写" | 考虑 **Aurora**(若仍不够 → DynamoDB) |

### 2.3 备份 & 恢复

| 方式 | 保留时长 | 何时用 |
|------|----------|--------|
| **Automated Backups** | 0–35 天 | 默认开启,**point-in-time recovery 到秒** |
| **Manual Snapshots** | 永久,直到你删 | 长期保留、跨账号共享 |
| **AWS Backup** | 中心化、跨服务 | 多服务统一备份策略 |

## 三、DynamoDB — 海量 NoSQL Key-Value

### 选 DynamoDB 的信号

题目里若出现以下任意,**优先考虑 DynamoDB**:
- "数百万 / 数十亿请求/秒"
- "毫秒级 / 亚毫秒延迟"
- "Serverless 完全托管"
- "schema-less"
- "无服务器后端 + IoT / 移动 / 游戏"
- "shopping cart, session store, leaderboard"

### 关键 feature

| Feature | 何时用 |
|---------|--------|
| **On-Demand vs Provisioned** | 不可预测流量 → On-Demand;稳定 → Provisioned + Auto Scaling |
| **DAX**(DynamoDB Accelerator) | 微秒级缓存,只对 DynamoDB |
| **Global Tables** | 跨 Region **多主**复制,本地读写 |
| **TTL** | 自动过期删除条目(session、临时数据) |
| **Streams** | CDC,触发 Lambda |
| **Transactions** | ACID 多项事务,跨表 |
| **PITR**(Point-In-Time Recovery) | 任意点恢复(35 天) |

### 容量陷阱

- **强一致读**(Consistent Read)**比最终一致读贵 2 倍**,延迟更高 — 题目说"成本最低" → **eventually consistent** 优先。
- **分区键设计**:高基数、均匀分布;否则会"hot partition"。

### DynamoDB vs RDS — 一句话

| 维度 | DynamoDB | RDS |
|------|----------|-----|
| 数据模型 | Key-Value / Document | 关系表 + JOIN |
| 扩展 | 无上限,自动 | 垂直扩 + 读副本 |
| 延迟 | 毫秒 | 毫秒–几十毫秒 |
| 一致性 | 最终 / 可选强一致 | 强一致 |
| 计费 | 请求 + 存储 | 实例 + 存储 |
| 适合 | 互联网级 | 复杂查询、事务 |

## 四、缓存层 — ElastiCache

### Redis vs Memcached

| 特性 | Redis | Memcached |
|------|-------|-----------|
| 持久化 | ✅ AOF + RDB | ❌ 纯内存 |
| 复制 / Multi-AZ | ✅ | ❌ |
| Pub/Sub、Sorted Set、Stream | ✅ | ❌ |
| 多线程 | 单线程 + cluster | 多线程 |
| 最适合 | 排行榜、会话、复杂结构 | 单纯水平扩存,只读热缓存 |

### 题目套路

| 题目说 | 答案 |
|--------|------|
| "缓解 RDS 读压力,毫秒查询" | **ElastiCache Redis**(若题目强调 leaderboard / session / 排行 → 一定 Redis) |
| "极简纯缓存、多线程" | **ElastiCache Memcached** |
| "DynamoDB 微秒级读" | **DAX**(不是 ElastiCache) |
| "无服务器缓存、按请求付费" | **ElastiCache Serverless**(2023 新出) |

## 五、专用数据库 — 一句话记忆

| 服务 | 一句话 | 关键词 |
|------|--------|--------|
| **Aurora** | 云原生关系型,RDS 的"高性能版" | 5× 性能、Serverless v2、Global DB |
| **DocumentDB** | MongoDB API 兼容 | JSON 文档、MongoDB 迁移 |
| **Neptune** | 图数据库 | 社交关系、欺诈检测、知识图谱 |
| **Timestream** | 时序数据库 | IoT 设备指标、应用监控 |
| **QLDB** | Ledger 账本,**不可篡改、加密哈希链** | 金融审计、供应链 |
| **Keyspaces** | Cassandra 兼容 | 已有 Cassandra 应用 |
| **MemoryDB for Redis** | Redis 兼容,**持久存储级别**(多 AZ 持久) | 主数据库 + Redis 接口 |

### 经典混淆题

| 题目说 | 答案 |
|--------|------|
| "金融交易,不可篡改、加密 hash 校验" | **QLDB**(不是 DynamoDB) |
| "社交网络好友推荐 / 欺诈关系图" | **Neptune** |
| "百万设备每秒上传温度" | **Timestream** + Kinesis Data Streams |
| "已有 MongoDB 应用迁云,不想改代码" | **DocumentDB** |
| "需要 Redis 接口 + 当数据库用(不只是缓存)" | **MemoryDB**(不是 ElastiCache) |

## 六、数据仓库 & 分析 — Redshift 家族

| 服务 | 何时用 |
|------|--------|
| **Redshift** | PB 级分析查询、BI 报表、复杂 SQL |
| **Redshift Serverless** | 不可预测分析负载 |
| **Athena** | **直接查询 S3 的 Parquet/CSV/JSON**,无需 ETL |
| **EMR** | 自管 Spark / Hadoop 集群 |
| **Glue** | Serverless ETL + Data Catalog |
| **Lake Formation** | 数据湖权限管理 |
| **OpenSearch** | 全文搜索、日志分析、Kibana |
| **QuickSight** | BI 可视化 |

### 关键决策

| 题目说 | 答案 |
|--------|------|
| "查询 S3 里的日志,SQL,无服务器,按查询付费" | **Athena** |
| "PB 级分析 + 跨多表 JOIN" | **Redshift** |
| "实时日志全文搜索 + 仪表板" | **OpenSearch** |
| "Serverless Spark ETL" | **Glue**(不是 EMR) |
| "可视化报表给业务部门" | **QuickSight** |

## 七、数据迁移 — 简要

| 服务 | 何时用 |
|------|--------|
| **DMS**(Database Migration Service) | 数据库 → 数据库迁移(同 / 异构) |
| **SCT**(Schema Conversion Tool) | Oracle → Aurora 这种**异构 schema 转换** |
| **DataSync** | 文件级别(NFS/SMB → S3/EFS/FSx) |
| **Snow 家族** | PB 级离线传输 |
| **Transfer Family** | SFTP/FTPS/FTP 上传到 S3 |

**陷阱**:
- 题目说"Oracle → Aurora MySQL,异构" → **SCT + DMS**
- 题目说"NFS share → S3" → **DataSync**(不是 DMS)
- 题目说"50 TB,带宽差" → **Snowball Edge**
