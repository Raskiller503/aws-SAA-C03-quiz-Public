# 06 · 解耦与事件驱动 — SQS / SNS / EventBridge / Kinesis / MSK

> "应用 A 直接调用应用 B" 是 SAA 题里的反模式。每次出现"前端忙不过来 / 一个挂了影响所有 / 突发流量打挂",答案都是 — **加一个解耦层**。

## 本章先懂这些词

解耦的意思是:不要让服务 A 必须等服务 B 立刻成功。中间放队列、主题或事件总线,可以削峰、重试、隔离故障。

| 术语 | 白话解释 | 常见考法 |
|------|----------|----------|
| **Producer** | 生产消息的一方 | Web/API/Lambda 把任务放出去 |
| **Consumer** | 消费消息的一方 | Worker/Lambda 慢慢处理任务 |
| **Queue** | 队列,一条消息通常给一个消费者处理 | SQS |
| **Topic** | 主题,一条消息广播给多个订阅者 | SNS |
| **Pub/Sub** | 发布/订阅模式 | 一对多通知 |
| **Fan-out** | 一个事件分发给多个下游 | SNS -> 多个 SQS |
| **Idempotency** | 重复执行也不会造成错误结果 | SQS Standard 可能重复,应用要能处理 |
| **Replay** | 重新读取历史事件 | Kinesis / EventBridge Archive 高频 |

## 一、第一性决策树

```
                你需要怎么传消息?
                       │
   ┌───────────────────┼───────────────────────────┐
   │                   │                           │
点对点队列         一对多扇出                   实时流式数据
(消费后删)        (订阅者收)                   (重放、多消费者)
   │                   │                           │
   ▼                   ▼                           ▼
  SQS                SNS                       Kinesis / MSK
                                       ┌──────────┴──────────┐
                                       Data Streams       Data Firehose
                                     (实时 + 重放)      (实时 → S3/Redshift)
                              事件驱动调度
                                   ↓
                              EventBridge
                              (跨服务、SaaS、规则匹配)
```

## 二、SQS — 简单消息队列

### 两种类型

| 类型 | 顺序 | 去重 | 吞吐 | 何时用 |
|------|------|------|------|--------|
| **Standard** | 不保证 | **可能重复**(at-least-once) | **无限** | 默认,削峰、异步 |
| **FIFO** | **严格按序**(按 Group ID) | **去重**(5 分钟窗口) | **300 TPS / 3000 TPS w/ batch** | 顺序关键、不可重复 |

### 关键参数

| 参数 | 默认 | 说明 |
|------|------|------|
| **Visibility Timeout** | 30 秒 | 消息被取出后,多久内不再可见 |
| **Message Retention** | 4 天 | 最长 14 天 |
| **Delivery Delay** | 0 | 最长 15 分钟 |
| **Long Polling** | 关闭 | **开启**减少空轮询费用,推荐 |
| **DLQ**(Dead Letter Queue)| — | N 次失败转到 DLQ,人工 / 自动处理 |

### 题目套路

| 题目说 | 答案 |
|--------|------|
| "削峰、异步、消费者用完删除" | **SQS Standard** |
| "**顺序、唯一**(转账)" | **SQS FIFO** |
| "消费失败后重试有限次再隔离" | DLQ |
| "消费者用一会儿才能处理完一条" | **延长 Visibility Timeout** |
| "Lambda 消费 SQS 怎么扩展" | Lambda **event source mapping** 自动 poll,SQS Standard 可达千并发 |

## 三、SNS — Pub/Sub 扇出

- **Topic** → 多个 **Subscriber**(Lambda、SQS、HTTP、Email、SMS、Mobile push)
- **不存储**消息(SQS 才存),订阅者必须在线或者把 SNS 推到 SQS 暂存
- **FIFO Topic**:配合 SQS FIFO 实现**有序广播**

### 经典模式:Fan-Out

```
              ┌─→ SQS Queue (Email service)
SNS Topic ───┼─→ SQS Queue (Analytics)
              └─→ SQS Queue (Notification)
              └─→ Lambda
```

订单事件 → SNS → 多个 SQS 队列,每个下游独立消费,**互不影响**。

### 题目套路

| 题目说 | 答案 |
|--------|------|
| "一个事件多个消费者各自处理" | **SNS → 多个 SQS**(fan-out)|
| "短信 / 邮件 / 推送通知" | **SNS** 直接订阅 |
| "**保证消息不丢**" + "**一对多**" | SNS + 多个 **SQS**(SQS 持久化) |
| "过滤订阅(只接受某属性的消息)" | **SNS Message Filtering** |

## 四、EventBridge — 事件总线(更高级)

| 维度 | EventBridge | SNS |
|------|-------------|-----|
| 模式 | 基于**事件规则**(JSON pattern matching) | 主题订阅 |
| Schema 注册 | ✅ Schema Registry | ❌ |
| 第三方 SaaS 集成 | ✅(Datadog、Zendesk、Shopify…)| ❌ |
| Replay | ✅(Archive + Replay)| ❌ |
| 自定义事件总线 | ✅ | — |
| 适合 | **事件驱动架构**、跨服务、SaaS 集成 | 简单广播 / 通知 |

### 题目套路

| 题目说 | 答案 |
|--------|------|
| "S3/EC2/任意 AWS 服务事件 → 触发动作" | **EventBridge** + 规则 |
| "定时触发 Lambda(cron)" | **EventBridge Scheduler**(或老的 CloudWatch Events)|
| "第三方 SaaS 产生事件,触发 AWS 内部" | **EventBridge SaaS partner** |
| "把过去事件重放" | **EventBridge Archive + Replay** |

## 五、Kinesis — 实时流式数据

### 家族成员

| 服务 | 一句话 |
|------|--------|
| **Kinesis Data Streams**(KDS) | 实时 + **可重放**(默认 24 小时,最长 365 天) |
| **Kinesis Data Firehose** | 实时 **→ 目的地**(S3 / Redshift / OpenSearch / 第三方);**无服务器、buffer & flush** |
| **Kinesis Data Analytics**(已改名 **Amazon Managed Service for Apache Flink**) | 流式 SQL / Flink 处理 |
| **Kinesis Video Streams** | 视频流入云 |

### KDS vs Firehose — 关键区别

| 维度 | KDS | Firehose |
|------|-----|----------|
| 数据保留 | 24 小时–365 天 | **不保留**(即时投递) |
| 处理 | 多个消费者并行读 + 重放 | 自动投递到目的地 |
| 延迟 | 毫秒 | **buffer 后 60 秒最低** |
| 扩展 | 按 **Shard** 数 | **完全自动** |
| 适合 | 实时分析、多消费者 | 数据入湖 / 入仓 |

### Kinesis vs SQS — 易混

| 维度 | Kinesis | SQS |
|------|---------|-----|
| 顺序 | 按 partition key | FIFO 模式才有序 |
| 重放 | ✅ 默认 | ❌(删了就没了) |
| 多消费者并行同份数据 | ✅ | ❌(每条只一个消费者) |
| 适合 | **流式分析、CDC、日志** | **任务队列** |

### 题目套路

| 题目说 | 答案 |
|--------|------|
| "IoT 设备每秒百万事件 + 实时分析" | **KDS + Flink + (Firehose → S3)** |
| "应用日志实时入 S3/Redshift" | **Firehose** |
| "处理顺序 + 可重放" | **KDS**(按 partition key) |
| "顺序但不需要重放" | **SQS FIFO** |
| "实时流式视频分析" | **Kinesis Video Streams + Rekognition** |

## 六、MSK — Managed Kafka

- 已有 Kafka 应用迁云 / Kafka 生态(Connect、KSQL、Schema Registry)→ **MSK**
- **MSK Serverless**:无脑扩展
- 不要把 MSK 当 KDS 的替代品考 — 题目里"已有 Kafka 经验" / "Kafka 客户端" 出现才选

## 八、混合编排模式 — SAA 常考的"组合拳"

### 模式 1:订单处理(削峰 + 扇出)

```
Web 前端 ──→ API Gateway ──→ Lambda ──→ SNS ──┬──→ SQS → 库存服务
                                              ├──→ SQS → 邮件服务
                                              └──→ SQS → 分析服务
```

### 模式 2:IoT 数据管道

```
IoT 设备 ──→ Kinesis Data Streams ──→ Flink (实时聚合)
                  │
                  └──→ Firehose ──→ S3 (数据湖)
                                       ↓
                                    Athena / Glue / Redshift
```

### 模式 3:跨服务事件总线

```
S3 事件 ──┐
EC2 事件 ─┼──→ EventBridge ──┬──→ Lambda
RDS 事件 ─┘                   ├──→ Step Functions
SaaS 事件 ────────────────────┘
```
